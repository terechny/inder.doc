
RabbitMQ. 

    Брокер сообщений с открытым исходным кодом, 
    который выступает посредником между различными сервисами или приложениями. 
    Он позволяет им «общаться», не дожидаясь ответа друг от друга в реальном времени.

    RabbitMQ решают три ключевые задачи:

    * Асинхронность: Позволяет приложению отправить запрос 
    (например, на создание PDF или отправку email) и сразу вернуться к пользователю, 
    пока «тяжелая» задача выполняется в фоне.
    * Отказоустойчивость: Если сервис-обработчик временно упал, 
    сообщения не пропадут — они накопятся в очереди и будут обработаны после восстановления.
    * Масштабируемость: Можно легко добавить больше «воркеров» (обработчиков) для разбора накопившейся очереди, 
    если нагрузка выросла.

    В основе работы лежит протокол AMQP (Advanced Message Queuing Protocol). Процесс обмена данными выглядит так:

    1. Producer (Издатель) — сервис, который отправляет сообщение.
    2. Exchange (Обменник) — принимает сообщение от издателя и решает, 
        в какую очередь его направить на основе правил (routing keys).
    3. Queue (Очередь) — временное хранилище сообщений на диске или в памяти до момента их прочтения.
    4. Consumer (Потребитель) — сервис, который забирает сообщение из очереди и обрабатывает его. 

    Основные типы обмена (Exchange Types)

    * Direct: Сообщение идет в конкретную очередь с точным совпадением ключа маршрутизации.
    * Fanout: Сообщение копируется во все очереди, привязанные к обменнику (рассылка всем).
    * Topic: Позволяет использовать шаблоны для маршрутизации 
    (например, orders.* отправит данные во все очереди, связанные с заказами). [8, 9] 

Apache Kafka.

    Распределенная система обмена сообщениями между серверными приложениями в режиме реального времени. 

    это распределенная платформа для потоковой обработки данных, которая работает не как классическая очередь 
    (как RabbitMQ), а как распределенный лог (журнал) записей.
    Главное отличие в логике
    В RabbitMQ сообщение удаляется сразу после того, как его прочитали. 
    В Kafka сообщения хранятся на диске в течение заданного времени (например, неделю), 
    даже если их уже кто-то прочитал. Это позволяет разным сервисам перечитывать 
    одни и те же данные с любой скоростью или возвращаться к ним позже.

    Основные компоненты

    Producer (Продюсер): Приложение, которое генерирует и отправляет данные в систему.
    Broker (Брокер): Сервер, на котором работает Kafka. Брокеры объединяются в кластеры для отказоустойчивости.
    Topic (Топик): Логическая категория, в которую записываются сообщения (например, «заказы» или «логи»).
    Partition (Партиция): Каждый топик делится на части (партиции) для параллельной обработки. 
    Сообщения внутри партиции строго упорядочены по их порядковому номеру — offset.
    Consumer (Консьюмер): Сервис, который сам запрашивает данные из Kafka (Pull-модель). 
    Он запоминает свой offset, чтобы знать, на каком сообщении он остановился.

   Как это работает (пошагово)

   1. Запись: Продюсер отправляет сообщение в определенный топик. 
      Kafka сохраняет его в одну из партиций в конец лога и присваивает ему уникальный offset.
   2. Хранение: Данные реплицируются (копируются) на другие брокеры. Если один сервер «упадет», 
      данные будут доступны на другом.
   3. Чтение: Консьюмер подключается и просит сообщения, начиная с последнего прочитанного им смещения (offset). Поскольку данные не удаляются, несколько разных консьюмеров могут читать один и тот же топик независимо друг от друга. [4, 8, 10, 12, 13, 14] 

   Почему это круто?

   Огромная скорость: Kafka может обрабатывать миллионы сообщений в секунду.
   Масштабируемость: Вы просто добавляете новые брокеры и партиции, чтобы увеличить пропускную способность.
   Надежность: Благодаря хранению на диске и репликации данные практически невозможно потерять.

OpenAPI 

    Индустриальный стандарт для описания REST API. 
    Это текстовый файл (обычно в формате YAML или JSON), который служит «паспортом» вашего сервиса.
    В этом файле четко прописано:

    Какие есть эндпоинты (URL-адреса).
    Какие методы поддерживаются (GET, POST, PUT, DELETE).
    Какие параметры нужно передать (в заголовках, в строке запроса или в теле).
    Какую структуру ответа ожидать (коды ошибок, форматы данных). [5] 

    Зачем он нужен?

   1. Документация: На основе OpenAPI-файла инструменты вроде Swagger UI автоматически рисуют интерактивную веб-страницу, где разработчик может потыкать кнопки и проверить работу API без написания кода.
   2. Генерация кода: Можно автоматически создать клиентские библиотеки (SDK) на разных языках программирования или заготовки для серверной части.
   3. Тестирование: Инструменты тестирования используют этот файл, чтобы проверить, соответствует ли реальный ответ сервера заявленному стандарту.
   4. Контрактный подход: Команды фронтенда и бэкенда могут договориться о формате данных (составить OpenAPI-схему) и работать параллельно, зная, что их части состыкуются. [6, 7, 8] 

Swagger

   Набор инструментов для работы с этим стандартом.
   Если OpenAPI — это чертеж здания, то Swagger — это инструменты, с помощью которых этот чертеж рисуют и по нему строят.
   Основные инструменты Swagger:

   1. Swagger UI — самый популярный инструмент. Он превращает скучный YAML-файл OpenAPI в красивую интерактивную веб-страницу. На ней можно увидеть все методы API и нажать кнопку "Try it out", чтобы отправить реальный запрос к серверу прямо из браузера.
   2. Swagger Editor — удобный редактор в браузере, где вы пишете описание своего API и сразу видите, как оно будет выглядеть в документации. Он подсвечивает ошибки, если вы нарушили стандарт.
   3. Swagger Codegen — утилита, которая берет ваш файл OpenAPI и автоматически генерирует код: либо клиентскую библиотеку (SDK), либо заготовку для сервера (Server Stub) на Java, Python, Go и десятках других языков.

   Почему это стандарт де-факто?

   Живая документация: Вам не нужно писать PDF-инструкции, которые устаревают через день. Документация обновляется вместе с кодом.
   Песочница: Тестировщики и фронтенд-разработчики могут проверять API без Postman или написания лишнего кода.
   Единый язык: Все участники разработки (менеджеры, аналитики, разработчики) видят одну и ту же структуру данных.


Scrum: Работа по расписанию

    Это жесткий каркас с четкими ролями и правилами. 
    Команда «запирается» на фиксированный срок (обычно 2 недели), чтобы выдать готовый кусок продукта.

    * Как это работает:
    1. Спринт: Отрезок времени (1–4 недели), за который нужно выполнить план.
    2. Планирование: В начале спринта команда берет задачи из общего списка (Backlog) и обещает их сделать.
    3. Дейли (Daily): 15-минутка каждое утро — что сделал вчера, что сделаю сегодня, какие есть проблемы.
    4. Демо (Review): В конце спринта показываем заказчику работающий код.
    5. Ретроспектива: Обсуждаем, как команда работала и что улучшить в процессах.
    * Роли: Скрам-мастер (следит за процессом), Product Owner (отвечает за ценность продукта), Команда разработки.

Kanban: Визуализация потока

    Здесь нет спринтов и дедлайнов для группы задач. Главное — чтобы задачи двигались по доске слева направо максимально быстро и без заторов.

    Как это работает:
    1. Доска: Колонки «Сделать», «В работе», «Тестирование», «Готово».
    2. WIP-лимиты (Work In Progress): Главная фишка. Нельзя брать в работу больше $N$ задач одновременно. Если колонка «Тестирование» забита, разработчики не берут новое, а идут помогать тестировщикам.
    3. Непрерывность: Как только задача готова, сразу берется следующая. Никаких пауз между итерациями.
    * Фокус: На сокращении времени цикла (Cycle Time) — от идеи до релиза.
